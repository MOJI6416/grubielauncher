# Подпись обновлений лаунчера (ed25519)

Лаунчер ставит обновление, только если файл установщика подписан нашим ключом ed25519. electron-updater сам сверяет sha512 скачанного файла с `latest*.yml`, но `latest*.yml` лежит в том же GitHub-релизе: кто получил доступ к репозиторию, тот подменит и установщик, и хеш. Подпись этот путь закрывает: без закрытого ключа подходящую подпись не сделать.

Закрытый ключ хранится в секрете окружения GitHub `update-signing`. Задача получает секрет окружения только после одобрения владельца (Required reviewers), поэтому запуск, который владелец не одобрил, ключа не видит. Без секрета всё работает, как раньше: релиз подписывается вручную на компьютере с ключом.

## Как устроено

- Открытые ключи — `src/main/utilities/updateSigningKeys.json` (основной `primary` и запасной `reserve`). Лаунчер принимает подпись любым из них.
- Закрытые ключи — у владельца офлайн (флешка, менеджер паролей). Основной ещё и в секрете `UPDATE_SIGNING_KEY` окружения `update-signing`. Запасной в GitHub не кладётся. В репозитории ключей нет и быть не должно.
- Подписывается строка `grubie-launcher-update\n<версия>\n<sha512 из latest*.yml>\n`. Подпись (base64) записывается в `latest*.yml` полем `signature` у каждого файла:

  ```yaml
  files:
    - url: grubie-launcher-2.2.7-setup.exe
      sha512: …
      signature: …
  ```

- Лаунчер в `update-downloaded` (и при старте, и в фоновых проверках) считает sha512 скачанного файла, находит его запись в `latest*.yml` и проверяет подпись (`src/main/utilities/updateSignature.ts`). Нет подписи, чужой ключ, другая версия или файл не совпал ни с одной записью — установщик удаляется, установка не начинается, игрок видит тост «Обновление не установлено», фоновые проверки до перезапуска не повторяются.
- Версия входит в подписанную строку, поэтому старый подписанный установщик нельзя выдать за новый.

## Выпуск версии

1. Тег `X.Y.Z` → workflow `Release Launcher` собирает Windows, Linux и (если включено) macOS и кладёт установщики и `latest*.yml` в черновик релиза.
2. Задача `publish` работает в окружении `update-signing` и ждёт одобрения владельца (Actions → запуск → «Review deployments» → «Approve and deploy»). До одобрения у задачи нет ни секрета, ни шагов.
3. Шаг **Sign update files**. Если в окружении есть `UPDATE_SIGNING_KEY`, шаг:
   - пишет ключ во временный файл в `$RUNNER_TEMP` с правами только владельца (`umask 077`, папка из `mktemp -d`);
   - убирает ключ из переменных окружения и запускает `node .github/scripts/update-signing.mjs sign X.Y.Z --key <файл>`: скрипт скачивает `latest*.yml` из черновика, проверяет, что ключ есть в `updateSigningKeys.json`, подписывает, сам проверяет результат и загружает файлы обратно;
   - удаляет папку с ключом в `trap … EXIT` — и при успехе, и при ошибке, и при отмене задачи (а виртуальная машина раннера после задачи всё равно уничтожается).

   Ключ в журнал не печатается; GitHub дополнительно маскирует значения секретов. Секрета нет — шаг пишет об этом и проходит.
4. Шаг **Check update signatures** (`update-signing.mjs verify X.Y.Z`) проверяет подписи. Если релиз не подписан (секрета нет или ключ не тот), шаг падает, черновик не публикуется — дальше по разделу «Подпись вручную».
5. Затем `publish` публикует релиз и «Что нового».

### Подпись вручную

Когда секрета нет или автоподпись выключена.

1. На компьютере с ключом (нужен `gh`, вошедший в аккаунт с правом записи), из папки `launcher`:

   ```bash
   node .github/scripts/update-signing.mjs sign X.Y.Z --key /путь/к/update-signing-primary.pem
   ```

   Если ключ зашифрован, пароль берётся из `UPDATE_SIGNING_PASSPHRASE`.
2. Перезапустить упавшую задачу `publish` (`gh run rerun <id> --failed`) и снова одобрить окружение. Она проверит подписи ещё раз и опубликует релиз.

Проверить подпись любого релиза: `node .github/scripts/update-signing.mjs verify X.Y.Z`. Локальные файлы (например, на Linux-стенде): `sign-files X.Y.Z --key <pem> latest.yml …` и `verify-files X.Y.Z latest.yml …`.

## Ключ в секрете окружения

Положить основной ключ (из Git Bash; файл передаётся через stdin и в истории команд не остаётся):

```bash
gh secret set UPDATE_SIGNING_KEY --env update-signing -R MOJI6416/grubielauncher < /путь/к/update-signing-primary.pem
```

Из PowerShell (там нет `<`): `cmd /c 'gh secret set UPDATE_SIGNING_KEY --env update-signing -R MOJI6416/grubielauncher < "C:\путь\к\update-signing-primary.pem"'`.

- Зашифрованный ключ (`-----BEGIN ENCRYPTED PRIVATE KEY-----`) — ещё `gh secret set UPDATE_SIGNING_PASSPHRASE --env update-signing -R MOJI6416/grubielauncher` (gh спросит значение).
- Только с `--env update-signing`. Секрет репозитория (без `--env`) видит любой workflow без одобрения — так класть нельзя.
- У окружения `update-signing` должен оставаться обязательный ревьюер-владелец: это и есть защита ключа. Не одобряйте запуск, которого не ждали (ветка, которую вы не пушили, чужой workflow).
- Желательно ещё ограничить окружение: Settings → Environments → `update-signing` → Deployment branches and tags → Selected branches and tags → ветка `main` и тег `*.*.*`. Тогда задачи из других веток окружение не получат даже на одобрение.
- Запасной ключ в GitHub не кладётся.

## Как отключить автоподпись

```bash
gh secret delete UPDATE_SIGNING_KEY --env update-signing -R MOJI6416/grubielauncher
gh secret delete UPDATE_SIGNING_PASSPHRASE --env update-signing -R MOJI6416/grubielauncher
```

Вторая команда нужна, только если пароль клали. Дальше релизы подписываются вручную, одобрение окружения остаётся. Workflow менять не нужно.

Если есть подозрение, что секрет утёк: удалить секрет, подписать следующий релиз запасным ключом и в этом же релизе поставить в `updateSigningKeys.json` новую пару (см. «Ключи»), затем положить в секрет новый основной ключ.

## Компаньон-мод

Тем же ключом подписывается манифест компаньон-мода (`companion/manifest.json` на CDN, лаунчер проверяет его в `src/main/companion/companionManifest.ts`). Workflow `Companion Release` (запуск вручную, вход `version`) работает в том же окружении `update-signing`: ждёт одобрения, скачивает jar и `targets.json` из публичного релиза мода, готовит и подписывает манифест (`.github/scripts/companion-release.mjs`, ключ — тем же способом через временный файл), отправляет его в api (`PUT /agent/companion-releases`, токен `RELEASE_AGENT_TOKEN`), а api сам кладёт jar и манифест в хранилище. В конце workflow читает манифест с CDN и сверяет sha256 каждого jar. Подробности и ручной запасной путь — `api/ops/companion-release/README.md`.

Без секрета `Companion Release` падает на шаге подписи — тогда манифест подписывается и выкладывается вручную по тому README.

## Ключи

- Новая пара (основной и запасной): `node .github/scripts/update-signing.mjs keygen <папка вне репозитория>`. С `UPDATE_SIGNING_PASSPHRASE` ключи шифруются. Скрипт печатает JSON для `updateSigningKeys.json`.
- Запасной ключ хранится отдельно от основного. Если основной потерян или скомпрометирован, релиз подписывается запасным, а в этом же релизе в `updateSigningKeys.json` ставится новая пара. Старые лаунчеры примут релиз по запасному ключу и дальше будут знать новые.
- При смене ключей копия открытых ключей нужна и в api (`ops/companion-release/signing-keys.json` и `src/companion-releases/companion-signing-keys.ts`), иначе api не примет новый манифест компаньона.
- Если потеряны оба ключа, автообновление сломается у всех: лаунчер придётся переустанавливать вручную с сайта. Поэтому у каждого ключа должна быть резервная копия.
- Закрытый ключ нельзя класть в секреты репозитория и на сервер api: секрет окружения с обязательным одобрением — единственное место в сети, где он лежит.
