# Подпись обновлений лаунчера (ed25519)

Лаунчер ставит обновление, только если файл установщика подписан нашим ключом ed25519. electron-updater сам сверяет sha512 скачанного файла с `latest*.yml`, но `latest*.yml` лежит в том же GitHub-релизе: кто получил доступ к репозиторию, тот подменит и установщик, и хеш. Подпись этот путь закрывает: закрытый ключ не лежит ни в GitHub, ни в CI, ни на сервере.

## Как устроено

- Открытые ключи — `src/main/utilities/updateSigningKeys.json` (основной `primary` и запасной `reserve`). Лаунчер принимает подпись любым из них.
- Закрытые ключи — только у владельца, офлайн (флешка, менеджер паролей). В репозитории их нет и быть не должно.
- Подписывается строка `grubie-launcher-update\n<версия>\n<sha512 из latest*.yml>\n`. Подпись (base64) записывается в `latest*.yml` полем `signature` у каждого файла:

  ```yaml
  files:
    - url: grubie-launcher-2.2.7-setup.exe
      sha512: …
      signature: …
  ```

- Лаунчер в `update-downloaded` (и при старте, и в фоновых проверках) считает sha512 скачанного файла, находит его запись в `latest*.yml` и проверяет подпись (`src/main/utilities/updateSignature.ts`). Нет подписи, чужой ключ, другая версия или файл не совпал ни с одной записью — установщик удаляется, установка не начинается, игрок видит тост «Обновление не установлено», фоновые проверки до перезапуска не повторяются.
- Версия входит в подписанную строку, поэтому старый подписанный установщик нельзя выдать за новый.

## Выпуск версии

1. Тег `X.Y.Z` → workflow `Release Launcher` собирает Windows, Linux и (если включено) macOS и кладёт установщики и `latest*.yml` в черновик релиза — как раньше.
2. Задача `publish` сначала выполняет шаг **Check update signatures** (`update-signing.mjs verify X.Y.Z`). Пока релиз не подписан, шаг падает с подсказкой, и черновик не публикуется. Если в настройках репозитория у окружения `update-signing` включено «Required reviewers», задача вместо этого ждёт одобрения.
3. На компьютере с ключом (нужен `gh`, вошедший в аккаунт с правом записи):

   ```bash
   node .github/scripts/update-signing.mjs sign X.Y.Z --key /путь/к/update-signing-primary.pem
   ```

   Скрипт скачивает `latest*.yml` из черновика, проверяет, что ключ есть в `updateSigningKeys.json`, подписывает каждый файл, сам проверяет результат и загружает `latest*.yml` обратно (`--clobber`). Сами установщики не трогаются. Если ключ зашифрован, пароль берётся из `UPDATE_SIGNING_PASSPHRASE`.
4. Перезапустить упавшую задачу `publish` (`gh run rerun <id> --failed`) или одобрить её в окружении `update-signing`. Она проверит подписи ещё раз и опубликует релиз.

Проверить подпись любого релиза: `node .github/scripts/update-signing.mjs verify X.Y.Z`. Локальные файлы (например, на Linux-стенде): `sign-files X.Y.Z --key <pem> latest.yml …` и `verify-files X.Y.Z latest.yml …`.

## Ключи

- Новая пара (основной и запасной): `node .github/scripts/update-signing.mjs keygen <папка вне репозитория>`. С `UPDATE_SIGNING_PASSPHRASE` ключи шифруются. Скрипт печатает JSON для `updateSigningKeys.json`.
- Запасной ключ хранится отдельно от основного. Если основной потерян или скомпрометирован, релиз подписывается запасным, а в этом же релизе в `updateSigningKeys.json` ставится новая пара. Старые лаунчеры примут релиз по запасному ключу и дальше будут знать новые.
- Если потеряны оба ключа, автообновление сломается у всех: лаунчер придётся переустанавливать вручную с сайта. Поэтому у каждого ключа должна быть резервная копия.
- Ключ нельзя класть в секреты GitHub Actions и на сервер api: тогда подпись перестанет защищать от взлома этих мест.
